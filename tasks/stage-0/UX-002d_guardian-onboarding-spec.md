## 🎯 Summary

- **기능명:** 보호자 온보딩 5단계와 `(public)` 화면 3종(랜딩·로그인·동의 안내)의 **디자인 명세** — 플로우·상태·문구·시각 규칙까지. 화면 코드는 짝 구현(`UX-002`)이 진다.
- **목적:** 개정 3.1이 디자인과 구현을 한 이슈로 합치면서 **디자인이 `FR-001`·`FR-010`·`FR-012` 뒤로 밀렸다.** 서버 경계가 없어도 확정할 수 있는 부분을 떼어 내 D+3에 착수한다.
- **왜 분리되나:** 원본이 스스로 적어 둔 대가가 이것이다 — *"🔴 FR 선행이 생겼다. 통합 전에는 디자인이 개발과 무관하게 먼저 갈 수 있었다."* 그 「먼저」를 되돌린다.

> **범위 경계 한 줄** — **동작이 필요한 것은 여기 없다.** 재개가 실제로 되는지, 실패 사유가 실제로 렌더되는지는 짝 구현이 판정한다. 이 태스크는 **무엇을 어떻게 보여줄지 확정**한다.

## ✅ Task Breakdown (실행 계획)

**온보딩 5단계**
- [ ] 5단계 **플로우 정의** — 각 단계의 입력 항목·필수 여부·다음 단계 조건
- [ ] **Stepper 시각 규칙** — 현재 단계 / 완료 단계 / 미착수 단계를 구별하는 토큰과 상태
- [ ] 🔴 **재개 상태 표기 설계** — *"2단계부터 이어서"* 문구 원문과 배치, 채워진 입력의 시각 표현
- [ ] 🔴 **카드 신청 실패 화면 설계** — 오류 사유 문구 원문(**사용자 언어**) · 입력값이 남아 있음을 알리는 표현
- [ ] **PWA 설치 유도 배너** — 5단계 내 배치 위치 · 문구 · iOS/Android 분기 안내

**`(public)` 화면 3종**
- [ ] 랜딩 · 로그인 · **동의 안내** 화면의 레이아웃과 문구
- [ ] 로그인 → 온보딩 **재개 지점 이동**의 사용자 표현

**공통**
- [ ] 각 화면을 **SRS §6.8 컴포넌트 대응표**에 사상 — 새 컴포넌트를 만들기 전에 표에서 먼저 찾는다
- [ ] 빈 상태·오류 상태·로딩 상태 문구를 **전 화면 전수** 확정
- [ ] `UX-001` 토큰만으로 표현되는지 확인 — 임의 색상 리터럴 0건

## ⚙️ Technical & Non-Functional Constraints

- **FR 선행 없음** — 서버 경계·반환 타입에 의존하는 결정을 이 태스크에 넣지 않는다. 필요해지면 그 항목을 짝 구현으로 넘긴다
- **스타일:** `UX-001`의 토큰·`src/components/ui/**`만으로 표현 — 별도 CSS·임의 색상 금지 (게이트 G5의 설계 쪽 절반)
- **접근성:** 아동 화면 기준(터치 ≥ 44px · 대비 4.5:1)을 낮추지 않는다. `(public)`·`(guardian)`도 대비 기준은 동일
- **판정 금지:** 단계 상태를 화면이 계산한다는 전제의 설계를 하지 않는다 — `FR-012` 반환값을 그리는 구조로 설계한다
- **iOS 분기:** 설치 배너는 자동 프롬프트가 없는 플랫폼을 전제로 문구를 쓴다 (X-3)
