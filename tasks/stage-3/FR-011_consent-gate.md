## 🎯 Summary

- **기능명:** 동의 4겹 판정 중 **2겹째(읽기 확정 판정)와 3겹째(쓰기 재확인)** 를 만든다.
- **목적:** CON-REG-01의 *"동의를 캐시하지 않고 세션 만료 시 재확인"* 은 **Next.js 기본값과 정면으로 부딪히는 요구**다 — App Router는 라우트를 정적으로 만들려 하고, **정적이 되는 순간 동의 상태가 굳는다.**
- **왜 한 이슈인가:** 읽기 차단과 쓰기 차단은 **같은 조회를 쓰고 같은 완료 판정(AC-T6.1 · T6.2)을 공유**한다. 한쪽만 있으면 REQ-NF-008의 「100% 차단」이 성립하지 않는다.

## 🧪 Acceptance Criteria (BDD/GWT)

**Scenario 1: 동의 미완 직접 접근 (AC-T6.1)**
- **Given:** 동의 미완 보호자 세션
- **When:** `/learn`에 직접 접근한다
- **Then:** 아동 화면이 **렌더되지 않고** `consent_gate_blocked`가 적재되며 **즉시 알림**이 발생한다.

**Scenario 2: 철회 후 즉시 차단 (AC-T6.2)**
- **Given:** 동의를 완료한 뒤 관리자가 **동의를 철회 처리**
- **When:** 아동이 **이미 열어 둔 화면을 새로고침**한다
- **Then:** **즉시 차단** — 캐시된 응답이 반환되지 않는다.

**Scenario 3: 쓰기 경로 차단**
- **Given:** 동의 미완 상태에서 Server Action을 **직접 호출**
- **When:** 액션이 실행된다
- **Then:** 래퍼가 **쓰기를 거부**하고 감사 로그를 남긴다 — 읽기 차단을 우회해도 쓰기는 막힌다.

**Scenario 4: 온보딩 세션 만료 재개 (ACE-8.2)**
- **Given:** 온보딩 중 세션 만료
- **When:** 재로그인한다
- **Then:** **직전 완료 단계에서 재개**되고 **동의 단계는 재확인**한다 — 동의는 캐시하지 않는다.

**Scenario 5: 4겹 정합성 (REQ-TEC-006)**
- **Given:** 4개 판정 지점 각각의 자동 테스트
- **When:** 임의의 한 지점을 제거한다
- **Then:** **그 지점의 테스트가 실패**한다 — 한 겹으로는 100% 차단을 증명할 수 없다.

## ⚙️ Technical & Non-Functional Constraints

- 🔴 **규제:** 동의 상태 **캐시 금지** (CON-REG-01 · REQ-TEC-006). `noStore()`가 빠지면 정적 최적화가 동의 상태를 굳힌다
- 🔴 **규제:** 동의 미완 진입 **100% 차단** (REQ-NF-008) — 부분 차단은 미충족이다
- **관측:** `consent_gate_blocked`는 **즉시 알림 · 30분 내 확인** 대상이다 (REQ-NF-017 — 라우팅은 FR-040)
- **경계:** 확정 판정 지점은 **`(child)/layout.tsx` 하나뿐**이다. 다른 곳에서 동의를 판정하면 지점이 늘어나 REQ-TEC-006의 「4개」가 깨진다
- **성능:** 매 요청 DB 조회가 §8.1 예산에 들어간다 — **캐시로 줄일 수 없는 비용**임을 예산에 반영한다
