## CORE-1 — 검증 4번 「es == max(선행 ef)」를 실측 불변식 7종으로 교체

**관찰** — 목표 §2가 명세한 forward-pass 조건 `es == max(선행 ef)`가 현재 편성에서 **10/46건 위반**이다.
`FR-001`(es=0)은 선행 `UX-001`(ef=3)이 끝나기 전에 착수하고, `FR-002`(es=4)는 `FR-001`(ef=9) 중간에 착수한다.

**원인** — 결함이 아니라 FASTTRACK 압축 편성의 수단이다. `parts` 필드가 태스크를 쪼개 **부분 착수 중첩**을 허용하고, 그것이 기준안 90일을 56일로 줄인 방법이다. 나아가 `es >= max(선행 es)`(44/46) · `ef >= max(선행 ef)`(45/46) · `ef == es + dur`(42/46)도 불변식이 아니다 — `parts`가 병렬이면 `dur`(총 작업량)과 `ef-es`(달력 구간)가 갈린다.

**영향** — 이 조건을 완료 게이트로 걸면 재편성과 무관하게 첫 실행부터 실패한다. 목표가 성립 불가해진다.

**결정** — 의존-타이밍 조건을 게이트에서 제거하고, 현재 편성에서 **46/46으로 성립하는 불변식**만 게이트로 쓴다.

| # | 불변식 | 현재 |
| --- | --- | --- |
| I1 | `start == 영업일(es)` · `target == 영업일(ef-1)` (기준 2026-09-07) | 46/46 |
| I2 | 선행 없음 → `es == 0` | 46/46 |
| I3 | `slack >= 0` | 46/46 |
| I4 | `critical ⇔ slack == 0` | 46/46 |
| I5 | `deps` 전건 실존 · 순환 0건 | 46/46 |
| I6 | `parts`의 `dur` 합 == 부모 `dur` · `parts` 구간이 부모 `[es,ef]` 내부 | 46/46 |
| I7 | `es == min(part es)` · `ef == max(part ef)` · 각 part의 `ef-es >= dur` | 46/46 |

> **처음 I7로 적었던 `ef - es <= dur`은 2건(`FR-034`·`FR-037`) 위반이라 폐기했다.** 두 태스크는 `parts` 사이에 **유휴 간격**을 갖는다 — `FR-034a`가 D+21~28에 끝나고 `FR-034b`가 D+35에 시작해 span 17 > dur 10이다. 다른 선행을 기다리는 정상 편성이므로, 구간을 부모↔part 경계 일치로만 검사한다.

**대신 강화한 것** — 의존 타이밍을 못 거는 대신 **짝 관계**를 검사한다. 구현 8건이 각각 대응 디자인 명세를 `deps`에 보유해야 한다(8/8). 이것이 「디자인이 구현보다 먼저」를 표현하는 검증 가능한 형태다.

**남는 위험** — 압축 편성이 임의 중첩을 허용하므로, 디자인 명세를 앞당겨도 **구현이 명세 완료를 기다린다는 보장은 일정에 없다.** 목표 조건 `max(es) <= 10`이 「앞당겨졌다」만 증명하고 「기다린다」는 증명하지 않는다. 이 간극은 `.agents/rules/007`에 사람이 지키는 규약으로 적는다.

## MINOR-1 — `_index.md`·`_summary.md` 검증을 행 수에서 ID 집합 일치로 교체

**관찰** — 목표 §2 검증 1번은 「`_index.md` 매핑 표 행 수」를 세라고 했다. 그 표는 `| #4 | \`FR-003\` | … |` 형태로 **GitHub 이슈 번호를 키로** 갖는다.

**영향** — 신설 디자인 명세 8건은 §4에 따라 **GitHub에 반영하지 않으므로 이슈 번호가 없다.** 행 수 검사는 원리적으로 맞출 수 없다.

**결정** — 세 원장(`태스크 파일`·`_index.md`·`_summary.md`)과 `manifest.json` 사이의 **태스크 ID 집합 일치**로 검사한다(`I1`). 행 수보다 강한 검사다 — 누락과 잉여를 각각 지목한다.

## CORE-2 — 디자인 명세의 `num`(이슈 번호)은 `null`로 두고, `project_setup.py` 대응은 범위 밖으로 남긴다

**관찰** — `manifest.json`의 모든 항목은 `num`(GitHub 이슈 번호)을 갖고, `scripts/github/project_setup.py`는 `sorted(M.values(), key=lambda x: x['num'])`로 정렬하고 `NID[o['num']]`으로 이슈 노드를 찾는다.

**영향** — 디자인 명세 8건에 어떤 값을 넣어도 그 스크립트는 깨진다. `null`이면 정렬에서 `TypeError`, `47~54`면 존재하지 않는 이슈로 `KeyError`다. 그런데 §4는 `project_setup.py` **실행을 금지**하고, 그 파일은 수정 허용 예외 목록에도 없다.

**결정** — `num: null`로 둔다. 47~54를 찍는 것보다 **깨짐이 시끄럽고 의미가 정확**하다(「이슈 번호가 아직 없다」). `project_setup.py`가 `num is None`인 항목을 건너뛰게 만드는 일은 **이 목표 범위 밖**이며, GitHub 원장을 46건에서 54건으로 늘릴지가 사람의 결정이기 때문이다.

**남는 위험** — 이 브랜치를 머지한 상태에서 누가 `project_setup.py`를 실행하면 즉시 실패한다. `.agents/rules/007`에 **선행 조건**으로 적고, `scripts/github/README.md`는 수정 허용 범위 밖이므로 손대지 않는다.

## MINOR-2 — 행위 기준(BDD/GWT) 전건을 구현 태스크에 귀속하고, 디자인 완료 판정은 「DoD 디자인 묶음」으로 한다

**관찰** — `UX-002`의 AC 3건은 전부 **동작하는 화면이 있어야** 판정된다(재진입 재개 · 외부 실패 렌더 · 세션 없는 렌더). 디자인 산출물만으로는 어느 것도 통과시킬 수 없다.

**결정** — 목표 §5의 보수적 기본값(*"판단이 서지 않으면 구현 쪽에 남긴다"*)을 적용해 **AC를 전건 구현에 남긴다.** 디자인 태스크의 완료 판정은 원본이 이미 명시한 것을 쓴다 — *"🔴 DoD가 두 묶음이다 — 「디자인 완료」와 「구현 완료」를 나눠 체크한다"*. 그 디자인 묶음을 디자인 태스크의 DoD로 옮긴다.

**DoD도 쪼개지 않는다** — 원본 DoD 8항목은 전부 *만들어진 화면의 성질*을 묻는다("Stepper가 시각적으로 구별하는가", "배너가 5단계에 있는가"). 이를 「규칙이 정해졌는가」(디자인)와 「규칙대로 구현되었는가」(구현)로 나누면 **한 항목이 두 개가 된다.** 그래서 **원본 DoD 8항목은 전건 구현에 남기고**, 디자인 태스크의 DoD는 원본이 「🔴 UX 선행」으로 **이미 열거한 산출물**의 확정 여부로 세운다.

**결과** — AC 총 개수 보존(디자인 0 + 구현 원본값) · 원본 DoD 개수 보존(전건 구현) · 디자인 DoD는 원본의 「UX 선행」 열거를 근거로 한다. **새로 만든 판정 기준은 없다.**

## MINOR-3 — `dur` 분배는 디자인 `round(원본 × 0.4)`(최소 1), 구현은 나머지

**결정** — 총 작업량을 보존하는 분배다. 원본 8건 합 **46일 → 디자인 18 + 구현 28 = 46일.**

| ID | 원본 | 디자인 | 구현 |
| --- | :-: | :-: | :-: |
| UX-002 | 6 | 2 | 4 |
| UX-003 | 6 | 2 | 4 |
| UX-004 | 13 | 5 | 8 |
| UX-005 | 4 | 2 | 2 |
| UX-006 | 7 | 3 | 4 |
| UX-007 | 3 | 1 | 2 |
| UX-008 | 3 | 1 | 2 |
| UX-009 | 4 | 2 | 2 |

**왜 MINOR인가** — 목표 §2가 CORE로 분류한 「분리 입도」는 *원본 1건을 몇 건으로 쪼개는가*이고 그것은 이미 2건으로 고정되어 있다. 여기서 정하는 것은 **크기 추정**이며 되돌리기 싸다.

## MINOR-4 — 디자인 태스크 일정은 `UX-001` 종료(D+3) 이후 2트랙 병렬, 파생 필드는 기존 규칙 승계

**관찰** — 말단 UX 8건 전건에서 **`slack = 56 - ef`** 가 성립한다(`FR-036`의 `ef=56`이 프로젝트 종료). `downstream`은 43/46에서 전이 후행 수와 일치한다(`FR-010`·`FR-012`·`UX-002` 3건은 원장 값이 낡았다 — 건드리지 않는다).

**결정**

- 디자인 8건을 `UX-001`(ef=3) 뒤 **2트랙 병렬**로 배치한다 — max(es) = **D+10** (기준 편성 D+25~42).
  - 트랙 A: `UX-002d`(3~5) → `UX-004d`(5~10) → `UX-006d`(10~13)
  - 트랙 B: `UX-003d`(3~5) → `UX-005d`(5~7) → `UX-009d`(7~9) → `UX-007d`(9~10) → `UX-008d`(10~11)
- 구현 8건은 **`es`를 바꾸지 않고** `dur`만 줄인다 → `ef` 앞당겨짐, `slack = 56 - ef`로 재계산. 임계 경로에 손대지 않는 가장 좁은 변경이다.
- `slack = 56 - ef` · `downstream` = 전이 후행 수 · `critical = (slack == 0)` · `parts` = 단일 구간 · `absorb = 0` · `num = null`(CORE-2).

**남는 위험** — 디자인 태스크의 `slack`은 프로젝트 종료 기준 상한이며 후행(구현)의 늦은 착수 기준 실부동이 아니다. 압축 편성이 임의 중첩을 허용해 CPM 부동을 재현할 수 없다(CORE-1). 디자인 ef ≤ 13, 구현 es ≥ 25로 간격이 12일 이상이라 실무상 구속되지 않는다.

## MINOR-5 — 검증 스크립트에 `--invariants-only` 추가

**관찰** — 목표 §2는 태스크 1건을 고칠 때마다 `validate_plan.py` 통과를 확인하라고 했다. 그런데 목표 조건 `G1`(디자인 8건 존재)은 **8건이 다 끝나야** 성립하므로 중간 단계에서 exit 0이 원리적으로 불가능하다.

**결정** — `--invariants-only` 플래그로 `I1~I6`만 검사해 건별 게이트로 쓴다. 최종 게이트는 플래그 없는 전체 실행(`I1~I6` + `G1~G5`)이다.
