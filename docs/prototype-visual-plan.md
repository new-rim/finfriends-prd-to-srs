## 1. 판정 목적 — 이 프로토타입으로 무엇을 판정하는가 *(T1)*

**결정: 화면 존재 확인.** 판정 문장은 *"임계치를 넘었는가"* 가 아니라 **"그 AC를 판정할 수 있는 화면이 존재하는가"** 다.

이것은 `UX-004` 원문 DoD가 **M 유형**(인터뷰 rubric)에 쓴 기준 그대로다.

> **M 유형 (화면 존재만 확인 · 판정은 α·β)**
> - [ ] `AC-1.1` · `1.2` · `1.3` · `3.2` — **인터뷰로 판정 가능한 화면**이 존재하는가? (기본 상태에서 무엇이 보이는지가 확정되었는가)

### 이 결정이 화면에 부과하는 것 — 그리고 부과하지 않는 것

| | 요구 |
| --- | --- |
| ✅ **요구한다** | **기본 상태**(상세를 펼치지 않은 상태)에서 **무엇이 보이는지가 확정**될 것 — `AC-1.1`·`AC-1.2`의 판정 대상이 기본 상태다 |
| ✅ **요구한다** | 화면 간 **문구 일치** — 4영역 명칭이 나무·학습에서 같아야 한다(`UX-001` Scenario 4 · `CON-REG-02`) |
| ✅ **요구한다** | 각 화면이 **어떤 AC를 어느 요소로 지는지**를 §5 대응표에 적을 것 — 이후 α 인터뷰의 설계 입력이 된다 |
| ⬜ **요구하지 않는다** | 문구의 **최종 확정** — 잠정 문구로 그리되 일치만 지킨다. 확정은 α 검수 뒤 |
| ⬜ **요구하지 않는다** | 응답자 모집 · 코더 2인 · Cohen's κ · 5초 노출 통제 도구 |
| ⬜ **요구하지 않는다** | rubric 코딩 · `k/8` 집계 |

### 🔴 어떤 AC도 「통과」로 적지 않는다

인터뷰를 실시하지 않으므로 `AC-1.1`·`AC-1.2`·`AC-5.6`은 **판정된 바가 없다.** PRD §3-0 ③의 표본 규칙(`n<5` → 판정 불가)을 논할 단계조차 아니다.

- 화면 검수 결과를 **PASS·달성·통과·검증**으로 적지 않는다. 커밋 메시지·보고서·문서 전부 해당한다.
- 적을 수 있는 것은 **「판정 가능한 화면이 존재한다」** 뿐이다.
- 정식 판정은 α·β 사용성 검수(§8-1 8슬롯)에서 난다. `UX-004` 원문이 *"α·β 사용성 검수 일정을 이 이슈와 함께 잡는다"* 고 적었다.

### 산출물

**§5 화면↔AC 대응표** — 3화면 각각에 대해 「이 AC를 이 요소가 진다」를 한 줄씩. 스크린샷을 함께 남긴다.
그것이 α 인터뷰의 **질문지 초안**이 된다 — 무엇을 가리고 무엇을 물을지가 이미 적혀 있는 상태로 넘긴다.

## 3. 나무 성장 단계·승급 조건 — 잠정 수치 *(T3)*

> 🔴 **이 절의 수치는 잠정이다.** PRD §7-3은 *"나무 성장 단계 수·조건 수치 · 매달 조건 상승 여부 — **팀 결정** · 프로토타입 착수 전(§8-4 ④)"* 를 **미결로 열어 두었다.** 아래는 **PRD 부록 B에 이미 적힌 값을 그대로 옮기고 비어 있던 한 칸만 채운 것**이며, §7-3 미결을 닫지 않는다.

### 3.1 단계와 조건

| 전이 | 학습 | 퀴즈 | 실천 | 출처 |
| --- | :-: | :-: | :-: | --- |
| **씨앗 → 새싹** | 1회 | 1개 | **1회** | PRD 부록 B *(「학습완주 + 퀴즈정답 + 실천 N회」 — 🆕 **N=1로 채움**)* |
| **새싹 → 나무** | **3회** | **5개** | **1회** | PRD 부록 B 그대로 |
| **나무 → 씨앗** | — | — | — | 주기 초기화 |

**주기** — 벌기 · 잘 쓰기 · 모으기 = **매달 초기화** / 불리기 = 적금 만기 주기 *(PRD 부록 B)*
**매달 조건 상승** — **없음(고정)** 으로 잠정. PRD에 값이 없다.
**정체 판정** — **14일 이상 미상승** *(PRD US-3 AC1 — 확정값 · 잠정 아님)*

### 3.2 🔴 이 수치를 옮기며 발견한 것 — 팀 확인 필요

**실천 조건이 두 전이에서 똑같이 1회다.** 학습·퀴즈는 1→3 · 1→5로 오르는데 실천만 1→1로 고정이다.
`AC-2.2`의 취지(*"퀴즈만 100개 풀어도 승급 불가 — 실천이 관문"*)를 생각하면 **뒤 단계일수록 실천이 무거워야** 자연스럽다. PRD 부록 B를 그대로 읽으면 그렇지 않다.

- **프로토타입은 위 표대로 그린다** — 임의로 고치지 않는다.
- **§7-3 팀 결정 때 이 항목을 함께 본다.** 이 문서가 그 입력이다.

### 3.3 화면이 이 수치로 만드는 것

| 화면 요소 | 근거 AC | 잠정 수치로 렌더되는 예 |
| --- | --- | --- |
| 승급 진행도 | — | 씨앗 · 새싹 · 나무 3단계 표시 |
| 「실천 N회 남음」 | `AC-2.2` · `ACE-2.3` | *"실천 1회 남음"* |

## 4. 4영역 아동 표기와 한 줄 설명 *(T4)*

> **결정: 화면에는 아동 표기만 쓴다.** PRD의 문서 명칭(벌기·잘 쓰기·모으기·불리기)은 **문서와 코드 식별자**로만 남고, 사람이 보는 화면에는 아래 표기가 나온다.

### 4.1 대응표 — 이 표가 단일 출처다

| 코드 식별자 | 문서 명칭 *(PRD)* | 🔴 **아동 표기 (화면)** | 한 줄 설명 |
| --- | --- | --- | --- |
| `EARN` | 벌기 | **벌어요** | 미션을 해내면 별을 받아요 |
| `SPEND` | 잘 쓰기 | **잘 써요** | 쓰기 전에 미리 적어두고, 지키면 별을 받아요 |
| `SAVE` | 모으기 | **모아요** | 갖고 싶은 걸 정하고 조금씩 모아요 |
| `GROW` | 불리기 | **늘려요** | 모아둔 돈이 시간이 지나면 스스로 늘어나요 |

### 4.2 「불리기 → 늘려요」로 바꾼 이유

PRD가 이 칸을 **감시 Pain으로 따로 잡아 두었다.**

> **A1(「불리기」 학습 장벽)** — 이자·복리가 어려워 「불리기」가 **학습 단계부터** 막힌다
> 실패 KPI — *4주제 중 「불리기」 학습 완주율이 최저이며 차상위와 격차 > 20%p*

「불리다」는 아동에게 뜻이 셋이다(부르다 · 물에 담그다 · 늘리다). **이름 자체가 A1의 장벽에 보탠다.** 「늘다」는 아동이 이미 아는 말이고 뜻이 하나다.
*(대안으로 「키워요」를 검토했으나 같은 화면에 성장 나무가 있어 「무엇을 키우는가」가 혼동된다 — 기각.)*

### 4.3 🔴 지켜야 하는 것

- **화면에는 아동 표기만.** 「벌기」·「불리기」가 화면에 나오면 안 된다.
- **네 화면이 같은 표기를 쓴다** — ① 나무 · ② 학습·퀴즈, 그리고 이후 ③ 회고·나머지 화면 전부. `UX-001` Scenario 4 · `CON-REG-02` · `REQ-NF-014`의 판정 대상이 이것이다.
- **표기와 설명은 코드에 상수로 한 곳에** 둔다 — `src/contracts/areas.ts`. 화면이 문자열을 직접 쓰지 않는다.
- `늘려요` 칸은 MVP에서 **실천 경로가 닫혀 있다**(F15 Could). 한 줄 설명과 함께 **「곧 열려요」** 가 뜬다(`AC-2.4`).

### 4.4 잠정으로 남기는 것

**아이콘 4종은 아직 없다.** PRD는 🌳 나무 · 🌲 숲만 표기한다. 프로토타입은 **아이콘 자리를 만들되 잠정 기호**를 쓰고, 확정은 `UX-001` 디자인 산출물로 넘긴다. `UX-001`의 *"색만으로 상태를 구별하지 않는다 — 문구·아이콘 병행"* 규칙은 **영역 식별이 아니라 상태 구별**에 걸리므로, 아이콘 미확정이 그 규칙을 깨지 않는다.

## 5. ① 성장 나무 화면의 시각 구조 *(T5)*

**결정: 변화 문장이 최상단.** 5초 안에 읽혀야 하는 것은 그림이 아니라 **「무엇이 어떻게 달라졌는가」** 다.

### 5.1 기본 상태 레이아웃 — 이것이 판정 대상이다

```
┌─────────────────────────────────────────────┐
│  이번 달, 잘 써요가 새싹이 됐어요.            │ ← 변화 문장   AC-1.1

├─────────────────────────────────────────────┤
│  ┌──────────┐  ┌──────────┐                 │
│  │ 벌어요    │  │ 잘 써요   │                 │
```

> 🧮 **위 수치는 §3.1과 검산된 값이다.** 모아요는 **새싹**이므로 다음 전이는 새싹→나무(학습 3 · 퀴즈 5 · 실천 1)다.
> 학습 1/3 · 퀴즈 2/5 · 실천 0/1을 채운 상태 → **남음: 실천 1 · 학습 2 · 퀴즈 3**. 가장 적게 남은 것이 실천이라 최상단에 온다.
> *(PRD US-2 `AC-E3`의 예시 「학습 2회 · 퀴즈 3개 남음」과 정확히 같은 상태다.)*
> 🔴 **씨앗 칸에 이 값을 쓰면 안 된다** — 씨앗→새싹은 학습 1 · 퀴즈 1 · 실천 1이라 「학습 2회 남음」이 **불가능**하다.

🔴 **Accordion·Dialog를 쓰지 않는다.** 위 정보는 **전부 펼치지 않은 상태**에 있어야 한다 — PRD US-1 AC2가 *"나무 상세를 펼치지 않은 기본 상태"* 를 판정 대상으로 못 박았다.

### 5.2 변화 문장 — 4가지 분기

rubric 세 요소를 문장이 직접 만든다: **① 비교 시점** `이번 달` · **② 변화 방향** `됐어요`·`자랐어요` · **③ 대상** `잘 써요`

| # | 조건 | 문장 | 근거 |
| :-: | --- | --- | --- |
| **1** | 이번 달 승급 **1건** | *"이번 달, **{영역}**이/가 **{단계}**이/가 됐어요."* | `AC-1.1` |
| **2** | 이번 달 승급 **2건 이상** | *"이번 달, **{영역A}**와/과 **{영역B}**이/가 자랐어요."* | `AC-1.1` |
| **3** | 승급 0건 · 실천 **1건 이상** | *"이번 달, 실천을 **{N}번** 했어요. 조금만 더 하면 자라요."* | 변화 방향을 「쌓임」으로 표현 |
| **4** | 실천 **0건** | *"아직 기록이 없어요."* + **첫 실천 안내** | 🔴 `ACE-1.1` — 빈 화면을 앱 결함으로 읽지 않게 |

> 🔴 **조사는 앞말 받침으로 갈린다.** 초판은 「{단계}**이** 됐어요」로 고정해 **「나무이 됐어요」**를 냈다
> (7R가 잡음). 「새싹」(받침 ㄱ)만 시연되는 동안 드러나지 않다가 「나무」 단계를 넣고 나타났다.
> `src/contracts/narrative.ts`의 `particle()`이 이/가 · 은/는 · 와/과를 고르며,
> `scenario.test.ts`가 **3단계 × 4영역 전부**를 돌려 재발을 막는다.

### 5.3 실천 근거 문장 — 「퀴즈를 많이 풀어서」를 막는 장치

`AC-1.2`는 *"퀴즈를 많이 풀어서"* 만 나오면 **실패**다. 그래서 변화 문장 바로 아래에 **무엇을 해서 자랐는지**를 영역별 동사로 붙인다.

| 영역 | 실천 근거 문장 |
| --- | --- |
| 벌어요 | *"미션을 **{N}번** 해내서 자란 거예요."* |
| 잘 써요 | *"쓰기 전에 **{N}번** 적어서 자란 거예요."* |
| 모아요 | *"**{N}번** 모아서 자란 거예요."* |
| 늘려요 | *(MVP에서 실천 경로 닫힘 — 문장 없음)* |

🔴 **학습·퀴즈 횟수를 이 문장에 넣지 않는다.** 4칸 격자 안에는 조건으로 표시되지만, **최상단 두 문장에는 실천만** 나온다.

### 5.4 나무를 무엇으로 그리나

**CSS/SVG 3단계 도형**(씨앗 · 새싹 · 나무)으로 그린다. **일러스트 에셋을 발주하지 않는다.**

## 6. 테마 분기 — 색 · 크기 · 타이포 3축 *(T6)*

**결정: CSS 변수 3축으로 가른다. 컴포넌트 복제는 0건이다.**

`UX-001`이 못 박은 조건 — *"🔴 아동/보호자 테마를 **변수로만** 분기 — 컴포넌트를 복제하지 않는다"*.

### 6.1 3축과 잠정 값

```css
/* app/globals.css — 유일한 CSS 진입점 */

:root {                      /* 공통 — 라운드·의미색·타이포 비율 */
  --radius-card: 12px;
  --ratio-scale: 1.25;
}

[data-theme="guardian"] {    /* ① 나무 화면 — 차분·정보 밀도 높음 */
  --touch-min:  40px;
  --space-unit:  4px;
  --text-body:  15px;
  --text-line:  1.5;

  --bg:         #F7F7F5;
  --surface:    #FFFFFF;
  --border:     #E3E3DE;
  --text:       #1F2320;   /* on --surface 15.9:1 */
  --text-muted: #5C625E;   /*              6.2:1  */
  --accent:     #2F6B4F;   /* 나무·성장 신호        6.3:1 */
}

[data-theme="child"] {       /* ② 학습·퀴즈 · ③ 회고 — 밝고 대비 높음 */
  --touch-min:  44px;   /* 🔴 요구값 — 내리지 않는다 */
  --space-unit:  6px;
  --text-body:  18px;
  --text-line:  1.7;

  --bg:         #FFFDF7;
  --surface:    #FFFFFF;
  --border:     #EDE6D6;
  --text:       #23201A;   /* on --surface 16.2:1 */
  --text-muted: #5E5849;   /*              7.1:1  */
  --accent:     #A35F00;   /* ⭐ 신호               5.0:1 */

  /* §8.1 회고 두 카드 — 🔴 둘 다 긍정 계열. 경고색(빨강·주황 경보) 아님 */
  --retro-earned: #E8F2E4;   /* 별 받음   — 「잘했어」 카드 배경 */
  --retro-review: #E6EEF5;   /* 별 없음   — 「따져보는」 카드 배경 */
}
```

> 🔶 **값은 전부 잠정**이다. 확정은 `UX-001` 디자인 산출물의 몫이다.
> 🔴 **내릴 수 없는 것 둘** — `--touch-min: 44px`(아동) · **본문 대비 ≥ 4.5:1**. 위 색값 옆의 비율은 `--surface` 위에서 잰 값이며, 색을 바꾸면 **다시 재고 L4로 확인**한다.
> 🔧 **`--accent` 교정 (2026-08-27 실행 중)** — 초판 `#B06A00`은 실측 **4.28**로 요구값 4.5 미달이었다. `#A35F00`(**5.0**)로 내렸다. **비율은 전부 실측값으로 교체했다** — `verify_prototype.sh`의 L4가 매번 다시 잰다.
> 🔴 **색 리터럴은 여기에만 있다.** `check:style`이 화면 코드의 색 리터럴을 0건으로 막으므로, 화면은 반드시 변수를 참조한다.

### 6.2 축을 3개로 잡은 이유

| 축 | 왜 필요한가 |
| --- | --- |
| **색** | 아동/보호자 화면이 다른 곳임을 즉시 알린다 |
| **크기** | 🔴 **강제됨** — 아동 터치 타깃 ≥ 44px은 색으로 표현할 수 없다 |
| **타이포** | 아동 3화면 중 **2개가 읽기 화면**이다(② 학습 원고 · ③ 회고 문장). `UX-001`이 *"아동이 읽을 수 있는 수준인지 검수 기준"* 을 항목으로 두었으므로 **어차피 정해야 하는 값**이다 |

### 6.3 지켜야 하는 것

- 테마는 **라우트 그룹 레이아웃에서 한 번만** 건다 — `app/(guardian)/layout.tsx`에 `data-theme="guardian"`, `app/(child)/layout.tsx`에 `data-theme="child"`. 컴포넌트가 테마를 판단하지 않는다.
- 🔴 **컴포넌트 복제 0건** — `src/components/ui/**`의 shadcn 6종은 **하나씩만** 존재한다. `ChildCard`·`GuardianCard` 같은 쌍을 만들지 않는다.
- **`(ops)` 테마는 정하지 않는다** — 3화면에 `(ops)`가 없다. `globals.css`에 **주석으로 자리만** 남기고 확정은 `UX-008`이 올 때 한다.

## 7. ③ 회고 화면의 갈래 — 시각 2종 · 문장 3종 *(T7)*

**결정: 별을 받았으면 같은 모습으로 보인다.** 시각은 **「별 받음 / 별 없음」 2종**이고, 문장이 3종이다.

### 7.1 세 상황과 처리

계획 카드: *"분식집에서 5,000원까지"*

| | 실제 | ⭐ | `plan_met` | `category_met` | **시각** | **문장** |
| :-: | --- | :-: | :-: | :-: | :-: | :-: |
| **①** 계획 지킴 | 분식집 4,000원 | **1** | true | true | **A** | 1종 |
| **③** 업종 다름 | **문구점** 4,000원 | **1** | true | **false** | **A** *(①과 동일)* | 2종 |
| **②** 계획 넘김 | 분식집 7,000원 | 0 | false | — | **B** | 3종 |

### 7.2 왜 ③을 ①과 같은 시각으로 두는가

**③에서 아동은 별을 받았다.** ①과 결과가 같다.

시각을 3종으로 가르면 **별을 받은 아동이 다른 화면을 보고** *"어? 별은 받았는데 왜 다르지 — 내가 뭘 잘못했나"* 로 읽는다. 이것은 태스크 `UX-006`이 갈래 B에 대해 이미 금지한 것과 같은 실패다.

> 🔴 **갈래 B가 벌처럼 보이지 않게** — 경고색·부정 아이콘을 쓰지 않는다. `FR-021`이 ⭐를 안 줄 뿐 **차감하지 않는** 이유와 같다

②(별을 **못 받은** 경우)조차 벌로 보이면 안 되는데, ③은 **별을 받은** 경우다. 더더욱 다르게 보일 이유가 없다.

**PRD가 요구한 것은 문장이다** — US-4 `AC-E2`: *"⭐1을 지급하되 **회고 문장을** 「업종 다름」 **갈래로 분기**하고 `plan_met=true` · `category_met=false`로 기록"*. 색 분기를 요구하지 않았다.

**판정 축도 2종이다** — US-5 `AC3`(=`AC-5.6`): *"**계획 초과일과 계획 준수일** … 부모가 두 경우를 화면만 보고 구분 ≥ 6/8"*.

### 7.3 🔴 태스크 파일과 어긋난다 — 기록

`tasks/stage-7/UX-006_plan-retro.md`는 이렇게 적었다.

> 🔴 **갈래별 색 분기** — 갈래 A(계획 준수) / 갈래 B(계획 초과) / **업종 다름**. **화면만 보고 구분 가능**해야 한다(AC-5.6)

**셋을 색으로 가르라고 읽힌다.** 이 문서는 그와 다르게 결정했으며 근거는 §7.2다.

- **`UX-006` 태스크 파일을 고치지 않는다** — 이번 범위 밖이고, 근거 문서는 구현 편의로 고치지 않는다(`CLAUDE.md`).
- **`FR-021`·`UX-006` 착수 시 이 판단을 다시 본다.** 그때 태스크 파일을 고칠지가 사람의 결정이다.

```
 │                  │             │  실제    7,000원  │
 │  적은 대로 썼어요!  │             │                  │
 │                  │             │  2,000원 더 썼어요 │
 │  분식집 4,000원    │  ← 보조     │                  │
 │                  │             │ 다음엔 어떻게 해볼까요?│
 └──────────────────┘             └──────────────────┘
    「잘했어」 카드                     「따져보는」 카드
```

| | 별 받음 | 별 없음 |
| --- | --- | --- |
| **주인공** | ⭐ 대형 | **금액 비교** 대형 (계획 → 실제) |
| **보조 정보** | 가맹점·금액 1줄 | 차액 · 다음 행동 문장 |
| **아이콘** | ⭐ | 🔍 *(돌아보기)* |
| **색** | 긍정 계열 A | 긍정 계열 B |

### 8.2 구조로 가른 이유

`AC-5.6`(**화면만 보고** 구분)과 「갈래 B에 경고색 금지」가 서로 당긴다. 보통 쓰는 초록/빨강이 막혀 있다.

- **색만으로 가르면** 몇 번 본 아동이 *"이 색 = 안 좋은 날"* 로 학습한다. 색이 결국 상벌이 된다.
- **아이콘·문구만 다르면** 두 화면이 너무 비슷해 `AC-5.6`의 *"화면만 보고 구분 ≥ 6/8"* 을 만들지 못한다.
- **구조가 다르면** 별 없는 쪽이 **나쁜 화면이 아니라 「다른 일을 하는 화면」**이 된다 — 혼내는 것이 아니라 **얼마나 차이 났는지 보여 주는** 화면이다.

### 8.3 🔴 금지

- **경고색**(빨강·주황) · **부정 아이콘**(❌ ⚠️ 😢) — 어느 갈래에도 쓰지 않는다
- **차감 표기** — `FR-021`은 별을 **차감하지 않는다**(P-03 「별은 모으기만」). *"-1"* 같은 표기가 있으면 안 된다
- **점수·등급·순위** — 회고는 평가가 아니다

### 8.4 단건 회고 vs 요약 회고

갈래와 **별개의 축**이다. 미완 회고가 3건을 넘으면 오래된 건이 **요약 회고로 병합**된다(`ACE-5.2`).

- 요약 회고 카드는 **몇 건이 묶였는지** 상단에 표시한다 — *"3일치를 모았어요"*
- 단건과 **테두리·여백으로** 구별한다. 갈래 구조(§8.1)는 그대로 안에 들어간다
- 큐가 비면 빈 상태 문구를 띄운다 *(문구는 T11)*

### 8.5 이 화면이 지는 AC

| AC | 이 요소가 진다 |
| --- | --- |
| `AC-5.6` | §8.1 **두 카드의 구조 차이** |
| `AC-E2`(US-4) | §7.1 **「업종 다름」 문장 분기** *(시각은 별 받음과 동일)* |
| `ACE-5.2` | §8.4 **요약 회고 표기** |
| 접근성 | 아동 테마 — 터치 타깃 ≥ 44px · 대비 4.5:1 · 색 외 문구·아이콘 병행 |

### 9.2 문장을 쓴 기준

| 기준 | 근거 |
| --- | --- |

- 🔶 **이 9문장은 초안이다.** 최종 문장 풀은 `FR-021`(문장 풀)·`UX-008`(문장 풀 관리 화면)에서 확정된다.

## 10. ② 학습·퀴즈 화면의 원고 — 「잘 써요」 한 편 *(T9)*

**결정: 원고는 한 편만 쓴다.** 프로토타입은 `app/(child)/learn/spend` **한 경로만** 렌더한다.

**근거** — PRD F3의 선행 의존성이 *"콘텐츠 4주제 원고(**외부 선행**)"* 다. 실제 원고는 콘텐츠 담당이 따로 쓰며 아직 없다.
이 화면으로 확인하려는 것은 **「글이 이 화면에서 읽히는가」**(글자 크기 · 줄 간격 · 한 화면 분량 · 스크롤 길이)이고, **한 편이면 넷 다 보인다.** 네 편이 있어야 보이는 것은 없다.

**「잘 써요」를 고른 이유** — ③ 회고 화면과 **같은 주제**다. 배운 것(잘 쓰기) → 실제로 해봄(회고)이 두 화면에서 한 줄로 이어져 보인다.

### 10.1 원고 초안 — 「사기 전에 먼저 적어요」

> 용돈이 생기면 뭐부터 사고 싶어요?
>
> 가게에 가면 사고 싶은 게 자꾸 늘어나요. 그래서 다 사고 나면 *"어? 벌써 없네"* 할 때가 많아요.
>
> 그럴 때 도움이 되는 방법이 있어요. **가기 전에 미리 적어두는 거예요.**
> 어디에 갈 건지, 얼마까지 쓸 건지 적어두면, 가게에서 고민될 때 적어둔 걸 떠올릴 수 있어요.
>
> 적어둔 만큼만 쓰면 별을 하나 받아요.
> 넘겨도 괜찮아요. **별을 받지 못할 뿐, 갖고 있던 별이 없어지지는 않아요.**

**마지막 줄이 규제 원칙을 아이 말로 옮긴 것**이다 — PRD **P-03 「별은 모으기만」** · `FR-021`이 차감하지 않는 이유. 아이가 갈래 B 화면을 벌로 읽지 않게 하는 **첫 장치**가 여기 있다.

🔶 **이 원고는 초안이다.** 실제 원고는 `FR-014`(학습 원고·이수·퀴즈)에서 콘텐츠 담당의 것으로 교체된다.

### 10.2 나머지 3주제는 프로토타입에 없다

프로토타입은 **`learn/spend` 한 경로만** 만든다. **학습 목록 화면은 범위 밖**이므로 *"준비 중"* 같은 표기를 만들 자리 자체가 없다.

> 🔴 **혼동 주의** — 나무 화면 4칸의 **「늘려요 → 곧 열려요」**(§5.1)는 프로토타입 사정이 아니라 **제품 사양**이다. PRD §4-4: *"「불리기」 칸은 **학습만 열리고 실천은 닫힘**(F15 Could) — 화면에 **"곧 열려요"** 표시 필수"*. 학습 원고가 없는 것과 **다른 이야기**다.

🔶 문항은 초안이며 실제 퀴즈는 `FR-014`에서 콘텐츠 담당의 것으로 교체된다.

## 12. 빈 화면 문구 3종 *(T11)*

**결정: 세 곳 모두 「지금 상태」 + 「그럼 뭘 하면 되는지」 두 줄.**

| **③** | 회고 화면 · 큐가 빔 | **지금은 돌아볼 게 없어요.**<br>계획을 적고 쓰면 여기에 나타나요. |

### 12.1 둘째 줄을 세 곳 다 붙인 이유

PRD `ACE-1.1`이 요구한 것은 ① 하나뿐이다 — *"「아직 기록이 없어요 + 첫 실천 안내」가 표시되고, **빈 화면을 앱 결함으로 인식한 응답자 ≤ 2/8**"*.

그러나 **그 오해는 ②③에서도 똑같이 생긴다.**

| 한 줄만 있으면 | 이렇게 읽힌다 |
| --- | --- |
| *"아직 기록이 없어요"* | *"우리 애가 안 하나? 고장났나?"* |
| *"곧 열려요"* | *"왜 나만 안 열려? 언제 열려?"* |
| *"돌아볼 게 없어요"* | *"왜 없지? 고장났나?"* |

②③은 **아동이 보는 화면**이라 오해가 더 오래간다. 둘째 줄이 그것을 막는다.

### 12.2 🔴 ②는 프로토타입 사정이 아니다

**「곧 열려요」는 제품 사양**이다 — PRD §4-4 · `AC-2.4`. 「불리기(늘려요)」는 **학습만 열리고 실천이 닫혀 있다**(F15 Could). 프로토타입에 학습 원고가 한 편뿐인 것(§10)과 **무관**하다.

### 12.3 문구는 어디에 두나

`src/contracts/areas.ts`(4영역 표기·설명)와 같은 자리에 **상수로** 둔다. 화면이 문자열을 직접 쓰지 않는다 — §4.3과 같은 이유다.

### 14.2 `app/page.tsx` — 진입점

계획 초판에는 **화면 간 이동이 0건**이었다. 보는 사람이 URL 세 개를 따로 쳐야 했다.

| `/tree?state=empty` | 실천 0건 · 4칸 전부 씨앗 | `ACE-1.1` 빈 화면 문구 · **씨앗 도형** |
| `/tree?state=grown` | 「잘 써요」가 나무로 승급 | 계획 §5.4의 **나무 도형** — 기본 시나리오에 승급 완료 칸이 없다 |
| `/retro?state=backlog` | 밀린 회고 2건 이상 병합 | `ACE-5.2` **요약 회고와 단건의 구별** — 기본은 1건만 묶인다 |
| `/retro?state=empty` | 회고 큐 빔 | 빈 화면 문구 |
| `/learn/spend?picked=b` | 퀴즈 정답 후 | ②→① 연결 문구가 스냅샷에 잡히게 |

🔴 **기본 시나리오(`RETRO_ENTRIES` 4건 · `AREA_STATES`)를 이 목적으로 바꾸지 않는다.** §14.1이 확정한 값이다.

**순서가 곧 주장이다** — PRD §0-1의 위계(*"선언①이 일어나야 선언②가 보여줄 것이 생긴다"*)를 링크 순서가 그대로 재현한다.
🔴 이 화면은 **프로토타입 전용 진입점**이며 제품 사양이 아니다. `FR-010`(인증·라우팅)이 오면 사라진다. `app/page.tsx`에 그 취지를 주석으로 남긴다.

## 13. 이 프로토타입이 **확인하지 않는 것** *(T12)*

빠진 것을 적어 두지 않으면, 나중에 *"프로토타입에서 봤는데?"* 가 근거로 쓰인다. 아래는 **본 적 없는 것**이다.

### 13.0 🔴 가장 큰 공백 — 아이 쪽에서 선언①이 닫히지 않는다

> **AZTKS 검토 1라운드가 T축에서 지적한 것이며, 3화면을 유지하기로 한 결정에 따라 여기 명시한다.**

PRD 부록 B의 **3층 구조** 중 **아이 층(⭐ 별)의 종점이 3화면에 없다.**

| 층 | 무엇 | 3화면에 있나 |
| --- | --- | :-: |
| ⭐ **별** *(아이 · 즉각 보상)* | 잔액 · 옷 구매로 **쓰는 곳** | ❌ **없음** |
| 🌳 **나무** *(부모 · 이번 주기)* | ① 성장 나무 | ✅ |
| 🌲 **숲** *(부모 · 장기)* | 월간 숲 | ❌ 없음(§13.1) |

아이가 별을 **버는** 순간은 ②(퀴즈 정답)·③(회고)에 있다. 그러나 **쌓인 별을 볼 곳도, 쓸 곳도 없다.** PRD가 이 층의 무게를 못 박아 두었다.

> **F5 아바타·옷장** — 아이의 **유일한** 동기 장치. **나무는 부모 화면 전용**

따라서 이 프로토타입은 **아이가 왜 계속하는가**(선언① 「성장이 일어난다」의 동기 쪽)를 **보여주지 않는다.** §10.1 원고가 *"갖고 있던 별"* 을 말하지만 그 별을 볼 화면이 없다.

- **의도된 결정이다.** `docs/prototype-lite-scope.md` §8의 Tier 2(위시리스트)로 미뤘다.
- **이 공백을 「프로토타입에서 확인했다」로 덮지 않는다.** 아이 동기 설계의 검증은 **위시리스트 화면이 생긴 뒤**다.
- **다음 Tier를 정할 때 이것이 1순위다** — §13.3의 미션 목록보다 앞선다.

### 13.1 화면이 없어서 못 보는 것

| PRD 근거 | 무엇 | 어느 화면이 있어야 하나 |
| --- | --- | --- |
| **US-6 `AC3`** | 아동 화면의 **「대기 중」 ↔ 「미실천」 시각 구별** | **미션 목록** — 둘을 나란히 놓아야 다른지 보인다 |
| **US-6 `AC-E1`** | **「승인되지 않음 + 사유」** ↔ 「미실천」 구별 | 미션 목록 |
| **US-1 `AC3`**(=`AC-1.3`) | 월간 숲에서 **60초 내 전월 대비 3개 지목** | 월간 숲 |
| **US-1 `AC-E2`**(=`ACE-1.2`) | **"다음 달부터 비교할 수 있어요"** · 델타 0 렌더 금지 | 월간 숲 |
| **US-4 `AC3`**(=`AC-4.3`) | 계획 없는 결제 → **작성 유도** | 계획 카드 |
| **US-8 `AC1`**(=`AC-8.1`) | 온보딩 **재개 · 재입력 0건** | 보호자 온보딩 |
| **US-8 `AC2`**(=`AC-8.2`) | 카드 대기 중 **잠금 범위** | 카드 잠금 |

> **엄마 쪽 「승인 대기 N건」은 만들었다**(§5.1 · `AC-6.2`). **아이 쪽 「기다리는 중」만** 빠진다.

### 13.2 프로토타입 자체로 확인 불가능한 것

| 무엇 | 어디에서 확인되나 |
| --- | --- |
| ⭐ 실제 지급 · 같은 세션 반영(`AC-2.1`) | `FR-013` · `FR-004` |
| 성능 예산 — 나무 p95 ≤ 1,250ms · ⭐ 반영 p95 ≤ 800ms | `FR-030` · `FR-033` · `FR-036` |
| 정합성 · RLS · 동의 게이트 · 오프라인 | `FR-003` · `FR-004` · `FR-011` · `FR-031` · `FR-036` |
| 인터뷰 rubric 판정(`AC-1.1` · `AC-1.2` · `AC-5.6`) | **α·β 사용성 검수** — 이 프로토타입은 **판정하지 않는다**(§1) |

### 13.3 다음 걸음

기본 3화면이 `docs/prototype-lite-scope.md` §6의 **L1~L5** 및 AZTKS 9라운드까지 통과함에 따라, 사용자 결정으로 §13.0과 §13.1의 미확인 화면 5종(위시리스트, 미션 목록, 월간 숲, 계획 카드, 소비 내역)을 프로토타입 범위로 구현 확장한다(§15 참조).
