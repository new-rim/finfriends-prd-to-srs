# [태스크 리스트] FinFriends — Next.js 기술 제약 반영판

**문서 ID:** TASKS-FINFRIENDS-NEXTJS-001
**개정 버전:** 3.1 — UI/UX 통합 · **55건 → 46건** *(개정 3.0: 밴드 C + 규칙 1 적용 · 153 → 55건)*
**기준 문서:** `SRS_finfriends-nextjs-v1_0.md` (SRS-FINFRIENDS-NEXTJS-001 · 개정 1.0)
**상위 문서:** `SRS_finfriends-v1_0.md` (SRS-FINFRIENDS-MVP-001)
**방법론:** `METHODOLOGY_task-extraction.md` · **통합 근거:** `ANALYSIS_task-consolidation.md` (개정 1.1) §4 · §6

> **개정 3.1에서 달라진 것 — UI/UX 통합**
> 개정 3.0은 화면 작업을 **디자인(`UX-*` 9) 과 화면 구현(`[UI]` 9)** 으로 나눠 관리했다. 같은 화면을 두 곳에서 좇는 부담이 커서 **한 이슈로 합쳤다** — `UX-001~009` **9건**이 디자인과 구현을 함께 진다(§2).
> 그 결과 개발 표에서 화면 9건이 빠져 **FR은 37건**이 되었고, 전체는 **55 → 46건**이다. ⚠️ 한 이슈에 디자인 완료와 구현 완료가 함께 들어가므로, **DoD를 두 묶음으로 나눠** 진행 상태를 구별한다.
>
> **개정 3.0에서 달라졌던 것**
> 개정 2.0의 **153건(FR 130 + UX 23)** 을 **55건**으로 통합했다. 태스크가 사라진 것이 아니라 **이슈 단위가 굵어진 것**이며, 흡수된 130건은 각 행의 「흡수」 칸에 전수 남아 있다.
> 병합 기준은 방법론 §2의 분할 규칙을 뒤집은 것이다 — *"담당자·검증 방식·완료 판정이 셋 다 같으면 한 이슈"*.
> **화면(`[UI]`)과 기능(`[Feature/*]`)은 합치지 않았다** — 방법론 §5가 `[UI]`를 둔 이유가 조회/렌더 병렬화이고, 합치면 기능이 디자인 완료를 기다리기 때문이다(분석서 §6).
> 남은 위험은 **§10에 전부 적어 두었다** — 절대 금지 목록과 충돌하는 병합 5건, AC 상한 초과 3건.
