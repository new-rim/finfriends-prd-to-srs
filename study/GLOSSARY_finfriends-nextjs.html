RLS

같은 요청이 두 번 와도 한 번만 처리되게 하는 고유 번호. 오프라인 아이가 재연결했을 때 ⭐가 두 번 들어가는 걸 막습니다.

가장 헷갈리는 짝

비슷해 보이지만 문서에서 전혀 다른 자리에 있는 것들입니다.

RSC와 Server Action은 둘 다 서버에서 도는데 뭐가 다른가?

RSC — 읽기

화면을 그릴 때 자동으로 돕니다. 사용자가 페이지를 열면 실행됩니다. 저장은 하지 않습니다.

Server Action — 쓰기

사용자가 버튼을 눌러야 돕니다. 저장·수정·삭제는 전부 여기서만 일어납니다.

이 둘을 나눠 둔 이유 — 어디서 데이터가 바뀌는지가 한 곳으로 모여야, 「⭐가 두 번 들어갔다」 같은 문제를 찾을 자리가 생깁니다.
배치가 왜 두 군데(pg_cron · Vercel Cron)로 나뉘어 있나?

pg_cron — 데이터베이스 안

시간 제한이 없어서 무거운 집계를 맡습니다. 월간 숲 스냅샷, 별 원장 정산처럼 아이가 늘어날수록 오래 걸리는 일.

Vercel Cron — 서버 쪽

외부에 연락해야 하는 일만 맡습니다. 푸시·문자 발송, 청구서 조회처럼 바깥을 두드려야 하는 일.

나누지 않으면 — 월간 집계가 아이 수백 명일 땐 잘 돌다가, 수천 명이 된 어느 달 1일에 시간 초과로 실패합니다. 그날 보호자가 보는 건 「다음 달부터 비교할 수 있어요」입니다.
동의 확인을 왜 네 군데서나 하나?

빠른 검사 (Middleware)

쿠키만 봅니다. 빠르지만 틀릴 수 있습니다 — 쿠키는 낡을 수 있으니까요.

확정 검사 (화면·저장·DB)

데이터베이스를 직접 봅니다. 정확하지만 느립니다. 그래서 아동 영역 진입과 저장 시점에만 겁니다.

「100% 차단」은 한 겹으로는 증명할 수 없습니다. 세 겹을 다 우회한 경로가 있어도 마지막에 데이터베이스가 행을 주지 않습니다.
「캐시하지 않는다」가 왜 규제 요건이 되나?

캐시란

한 번 만든 화면을 저장해 뒀다 다시 쓰는 것. 빠르지만 값이 낡습니다.

동의 상태는 예외

동의가 철회됐는데 저장된 화면이 나오면 동의 없이 아동 화면이 열립니다. 그래서 이것만은 매번 새로 확인합니다.

성능 예산(1,250ms) 안에서 이 확인에 60ms를 고정으로 배정해 뒀습니다 — 「깎을 수 없는 칸」으로 표시된 이유입니다.
